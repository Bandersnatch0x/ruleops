# 想法压力测试：扫描完整性值得一个独立执行层吗？

## 1. 决策建议与投入边界

**recommendation: pause to run the experiment。** 保留现有 Java 本地 / Shadow 执行能力和必要安全维护，暂不加投独立平台、生产阻断、控制台、插件或拆仓；先完成一批有原始任务材料和真实资源承诺的需求访谈。不是暂停已有正式窗口，也不是修改既有 ADR；本报告只提出待用户裁决的投资建议。[R1][R2][P2]

- **time / money / attention**：建议一次最多 **21 个日历日、14 小时研究方总工时、现金 0 元、新代码 0 行**的实验；一个负责人执行，一位复核者只参与计数核验，双方时间都计入上限。8 位合格参与者各约30分钟，承诺核验另每人至多15分钟，明确披露参与者自身的时间成本。实际招募成本未知，不能保证零现金一定招满。
- **learning**：这笔有限、可逆的投入可以区分“现有工具已经够用”“有痛但不值得增加一层”“愿意为当前 Shadow 边界投入真实资源”。它不证明付费、留存或规模；仍比继续开发、再跑一次作者演示更直接地改变本轮投入判断。
- **stop spending**：到任一上限就提交 positive / negative / unknown，不以样本不足为理由无限延期，也不以加功能换受访者的附和。批准前不招募、不接触任何外部系统；本轮未实施实验。

**证据强度**：可确立本次读到的代码行为和声明边界（conclusive，仅限静态检查事实）；可交付、独立采用的整条链证据 weak；真实需求、愿付费、留存与商业模式 unknown。对“先实验而非继续扩建”的建议是决策推断，不是市场已失败的结论。

## 2. 核心论证：分析后重述

### 2.1 重建的想法、用户与预期结果

**core_argument**：对**实际负责 Java 仓库 CI 检查链的平台工程师**，在一次无告警、执行异常或模块变动后，完成“本次必需检查到底跑全没有，并把判断与下一步交给负责人”的任务；ERF 的冻结 ScanPlan、Completeness、三态结果及可复核证据，**假定**比该团队现有的 CI 状态、扫描器报告、构建日志和人工核对更能减少误判与复核成本，且收益超过接入和持续维护一层工具的成本，因此该工程师及其资源负责人会安排真实试用并在同类任务中选择复用。[R1][R3][P3][P4]

这里真正要检验的是**相对现有做法的增量价值是否足以换来投入**，不是“能否实现三态枚举”。不假设所有 CI 都只看告警数，也不假设现有扫描器不会识别失败；它们是否已经满足目标团队的需要，必须成为对照，而非被做成稻草人。

### 2.2 分级纪律：不继承前序报告的等级标签

本报告严格采用指定技能的证据口径：**A**=行为（付费、转化、已签署承诺、遥测或真实任务完成）；**B**=强直接（产品/客户数据、实际定价、采购或反复的第一方抱怨）；**C**=佐证（评论、从业者讨论、案例）；**D**=代理（搜索、招聘、融资、市场报告）；**E**=断言（README、文档或无背后材料的自述）。

02 §1、03 §6中的局部等级口径与本技能不一致，故只复用其来源线索，不把它们的“工程 D”“事件 C”“承诺 B”原样搬过来。**文档写了“真实演练”仍是 E 级陈述；若找到了可核对原始行为材料，只对它实际证明的事实升级。** 源码与测试另标 `implementation fact`，因为源码不是需求代理指标；没有客户事实时，关联需求主张仍为 E / unknown。签署试用承诺即使属于 A，也不是付款、留存或产品优越性的 A。

### 2.4 Collapse conditions

1. **task collapse**：合格目标对象能展示现有流程已正确发现/处理执行缺口，实际优先问题在别处，又不肯为独立层投入资源——取消“这个群体现在需要独立完整性产品”的前提。
2. **advantage collapse**：问题确实存在，但已有输出/小范围配置修正足够，或新增分母配置、包/信任维护与解释成本吃掉收益——技术存在不等于产品胜出。
3. **boundary collapse**：对方只愿为生产阻断、审计认可的正式证明或其它当前禁用能力买单，对只读Shadow无投入——当前最小交付无法通向所声称的价值，不追加未来承诺换认可。
4. **truth collapse**：输出完整但必需范围建模错误、用户把exit0当PASS，或证据接收者不能复核——真实判断任务没有完成，不能用工程演练PASS替代。
5. **business collapse**：后续得到试用却得不到有触发机会的复用或资源负责人支持——只能支持一次性验证/服务，不足以支持独立平台；本轮尚不能断言这一结果已发生。

这些是理论失效的条件，不是本次已观察到的客户结论；本轮可执行的杀死规则只覆盖第1–3项的早期资源投入命题，见§4。

## 3. 单一瓶颈信念与实验选择

**bottleneck_belief**：**负责Java CI的平台工程师，是否因现有工具仍留下代价足够高的扫描完整性判断缺口，而愿意让真实资源负责人为一个不授予生产权威的独立Shadow执行层安排自有资源。**

这是一个“相对现有替代品是否值得投入”的不确定性，不拆成需求、购买、留存三个并列瓶颈。功能可用性、范围分母与正式窗口质量仍重要，但即使全部通过，也不能替这条信念作答。

**decision_flip**：支持信号成立，则由 `pause to run the experiment` 转为建议 `keep building` 的**有界含义**：只批准对已承诺真实任务做接入/判读验证及必要缺口工作，仍须用户裁决，不是全面恢复建设或证明商业成立。杀死条件成立，则建议 `stop` 当前目标群体的独立执行层扩建论证；没有更强邻近证据就不自动redirect。其余结果保持暂停/unknown，而不是解释为默认支持。

没有编造预期信息增益分数或成功概率。选择的是**当前最可能改变投入决策、而非最容易得到正面结果**的实验。

### 4.2 动作与时间顺序

1. **Day 1–3：固定协议，约到合格对象。** 冻结8人目标、资格、计数/拒绝规则、支持和杀死阈值、21日截止及14小时工时账。零现金意味着不用礼品、折扣、免费定制或佣金购买“愿意试用”；无法招募则记录可达性未知，不先开发招募工具。
2. **Day 4–14，每人30分钟，前20分钟不pitch。** 最先只问“最近最占你时间/风险的三个CI检查问题是什么”，逐字锁定top-3，之后才按03的Q1–Q4回放最近一次实际任务：看什么输出、怎样判定完成、谁接下一步、实际返工/人力及已采用办法。最后补充既有脚本的具体异常问题。**在提示完整性、零告警、SpotBugs或介绍产品后才出现的痛点，不计无提示top-3**；否则原脚本的提示会污染自己的成功指标。[R6][P3]
3. **在同一回放里给替代品公平获胜机会。** 请对方用现在的CI状态、引擎日志/已有脚本说明同一任务如何判断；优先找已正确失败、已正确补跑、未发生额外损失或配置修正已解决的材料。原话只是E；有直接客户数据可B；观察到真实工作绕行/任务完成可A。不能核对成本时记unknown，不代估金额。历史事故不强求重演，现有正常流程同样是有效对照。
4. **后10分钟才介绍受限概念并要行动。** 只展示当前“Java、本地/Shadow、完整性相对冻结计划、无生产阻断/SCM写入”的说明，并提醒完整FAIL也可exit0；不演示未分发能力，不声称已经能证明规范全覆盖。问“刚才哪一步它能替掉？哪一步你已有工具更好？值得试还是完全不值得？”先记拒绝和前置条件，再让对方自行选择是否安排真实投入。[R1][R3][R9]
5. **Day 15–19：最多每人15分钟核验承诺，不补卖功能。** 仅认可已落实的以下一种：真实仓库的只读Shadow排期（具名操作者/资源负责人已确认、明确仓库匿名ID、日期、至少90分钟自有工时），或双方确认的一页试用意向（写明同等具体范围与资源），或已经发生且由预算/资源负责人确认进入上述具体验证排期的引荐。排期应在访谈后30日内，且明确接受无生产权威的边界。仅发日历邀请、口头“有兴趣”、答应将来介绍老板、无资源条款的意向，不算。排期是承诺，**不是已完成试用，更不是已付费**。
6. **Day 20–21：复核者盲于研究者推荐，核对证据后判读。** 逐人检查top-3发生在提示前、对照材料支持什么、承诺是否真实和有条件、是否来自不同组织；交付一份分母完整的汇总。访谈者不能把对方未确认的推测写成事实。到任一预算上限即收尾；本轮不执行Shadow试用、不帮客户跑仓库、不增加运行/遥测系统。

承诺所需的未来Runtime/规则前置必须如实披露：真实Java包与Candidate的外部可得性尚未在本次确认；若对方只在“你先补未交付功能”时才愿排期，记录为条件性兴趣，不计落实承诺。不能用reference/fake包绕过这个限制，也不能把安装资产未具备造成的障碍说成用户没有需求。[R4][P5]
