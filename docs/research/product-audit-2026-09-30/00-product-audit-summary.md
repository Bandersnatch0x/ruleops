## 3. 贯穿六项的共同结论

1. **工程可信、边界清楚，但需求不可判。** 六项一致确认：完整性、三态 Gate、冻结 ScanPlan、`LOCAL_UNATTESTED`/SHADOW 边界有真实实现与历史演练；同时一致确认：真实需求、使用频率、切换与付费意愿**全部为 E / unknown**。
2. **对外主线应收紧到执行层。** 01（推荐 A）、02（pause to validate）、04（`local-shadow-execution-evidence`）、05（Keep 集中于 init/scan/结果）在同一方向上收敛；创作、治理、Pilot 研究、IDE、Server 读接口退居供货/内部/研究路径。
3. **下一步不是开发，是验证。** 02 的“8–12 场访谈”、03 的“五问切面”、06 的“IST-20260930-01 实验协议”是同一件事的三种细化——且都落在一个待验证的瓶颈信念上。
4. **没有一项审计授权扩建。** 05 的 Keep 6 亦注明“Keep≠现在开工”；04 的指标是待批准计划；06 建议 `pause`。六项对“继续大规模建设”**零支持票**。
5. **工程门禁状态本批未建立。** 六项均尝试 `bash scripts/check.sh` 失败（PATH 无 bash）或按其写入范围主动放弃运行；**报告验收 ≠ 产品门禁通过**，当前 HEAD 的全量门禁红/绿未建立证据。

## 4. 合并后的推荐与唯一下一步

**推荐：保持 Java 本地 / Shadow 执行层主线与必要安全维护，暂停一切对外扩建；先完成需求验证实验。**

**唯一下一步（三份报告指向同一动作）**：

- 由用户**指定一位研究负责人 + 一位复核者**；
- 执行 **8 位合格 P1 对象**的需求访谈（覆盖至少 4 个组织、每组织至多 2 人、至少一半非作者熟人）；
- 封顶 **21 个日历日 / 研究方 14 小时 / 现金 0 / 新代码 0**；
- 前置条件：**用户批准后才招募/接触**；正式 LIVE_SHADOW 窗口仍按其原治理条件独立执行，不被本实验覆盖。

**翻转信号（06 冻结）**：8 人中**≥4 人**在无提示情况下把完整性/绿灯可信度列为 top-3，其中**≥2 人**的真实任务材料可核对缺口与投入，且**≥2 个不同组织**落实自有资源承诺 → 建议转为**有界 keep building**（仅批准这些承诺任务的接入/判读验证）。

**杀死条件（06 冻结）**：**≥5 人**用材料说明现有流程足够或增量不值成本并拒绝 Shadow 投入，且**0 个组织**落实合格承诺 → 建议 **stop** 当前目标群体的独立层扩建论证（保留工程资产）。

**其余结果（mixed / unknown）保持暂停**，不得靠降低门槛、增加熟人或工程 PASS 补足。

**两条必须先定的执行细节（来自独立交叉核对，直接影响本实验有效性与预算边界）：**

- **X4｜实验条件严于既有脚本：** 06 的新增约束（≥4 组织、半数非熟人、2 个不同组织承诺、90 分钟自有工时）比 02/03 的既有访谈脚本更严，是**新提案、非已议定门槛**；批准前须逐条冻结，不能事后降门槛，也不能把原来的“承诺 B”自动当成“付费 A”。
- **X5｜提问顺序会污染成功指标：** 03 的访谈问题含异常/范围提示，而 04 要求“无提示 top-3”；若先问带提示的题，痛点就不能计为无提示。**须采用 06 的顺序（先锁定 top-3，再回放 03 的问题）**，否则翻转信号自证。

## 6. 证据纪律与置信度

- **可确立（conclusive，仅限静态检查事实）**：代码行为、命令边界、`rf gate` 拒绝、功能实现与测试入口存在性、交付资产的 reference/真实边界。
- **弱（weak）**：端到端可交付、由独立用户采用整条链的能力。
- **unknown**：真实需求、持续使用价值、愿付费、留存、商业模式、预算方、采购周期、可达性。
- **不成立为由**：“未发现证据”不等于“用户已拒绝”；本批未证明市场不存在，也未证明总市场存在。
- 所有 report 内嵌自检（Python 断言核对章节、条目、来源路径、HEAD 与哈希）均已通过；自检只覆盖报告结构，不替代产品验收。

## 7. 批内一致性与分歧

**顶层一致**：六项对“执行层主线 + Java 本地/Shadow + 需求 E/unknown + 暂停扩建”无相互矛盾；**没有任何一项宣称市场需求 / 付费 / 采用已经成立**，也没有后篇明确反转前篇的核心产品边界。**分歧集中在证据量尺、实验新增条件、时间基准与处置词的对象层次，不能抹平为“完全一致”。**

### 7.1 两处结构性问题

- **证据量尺不一致（不可忽略）**：02 §1 / 03 §6.1 用“工程 D / 事件 C / 承诺 B”的局部等级；**06 §2.2 明确声明该口径与本技能不一致并拒绝继承**，改用技能自身的 A–E（A=行为、B=强直接、C=佐证、D=代理、E=断言）。**这是定义分歧，不是哪篇推翻哪篇**：同一份真实签署承诺在 02/03 归 B、在 06 归 A；一次未核实的事件原话在 02/03 归 C、在 06 仍是 E。**处理规则：保留来源原等级与具体事实，不合并成“全体 A/B 证据”；另用 §6 的 conclusive / weak / unknown 标明结论对象。** 阅读 01–05 的“D 级工程证据”时不得误读为需求已被部分验证。
- **分母不可比**：01 的“12 个功能组”与 05 的“121 个细粒度入口”**粒度与覆盖层次都不同**。05 的 Keep＝6/121≈5.0% 是“本轮新增投资候选占比”，01 的 A 候选 7/12≈58% 是“与候选叙事的关联”，二者都不是完成率、需求命中率或市场份额；`Keep+Keep-as-is=58/121≈47.9%` 同样不可与 7/12 相比。API/协议逐项展开会放大入口分母，不增加独立购买任务。
